---
title: Mobile app integration
description: Prepare and register the native compatibility boundary owned by an Expo host app.
---

The Expo host owns embedded fallbacks, native compatibility, and public Worker
URLs. It does not contain mini-app source paths or release build commands.

```json title="app.json"
[
  "expo-lynx-view",
  {
    "embeddedBundlesPath": "./generated/expo-lynx/embedded",
    "publicKeyPath": "./keys/lynx/updates.public.pem",
    "deliveryEndpoints": {
      "merchant-home": "https://delivery.example.com/v1/bs-one/merchant-home"
    }
  }
]
```

The app and feature IDs in every URL must already be registered by the Console
operator. The host never creates them from its configuration.

## Embed, prepare/register, then build

```sh
# once per mini app: writes one shared iOS/Android embedded bundle
pnpm lynx host embed ../merchant-home

# local fingerprint + authenticated Worker registration for both platforms
pnpm lynx host prepare --register

# build and verify the native app outside this command
```

`host register` recalculates the native compatibility identity and fails if the
project changed since `host prepare`. This prevents a remote bundle for one
native build being selected for another. Do not change native dependencies or
the Expo Lynx plugin configuration between this command and the native build.

Run `host embed` only once when the embedded mini app changes. Before an
Android release, the default preparation already contains its runtime. Pass
`--platform` to `host prepare` only when the project intentionally targets one
platform. No second bundle directory is created.

If a released binary was not registered, devices receive a signed disabled
response and keep their embedded baseline. They never receive a bundle for a
different host build.

The host CI needs only `LYNX_DELIVERY_API_KEY` and `LYNX_DELIVERY_SERVER` for
registration. It does not need the Worker signing private key or R2 credentials.

## Warm the runtime in the host

Once the host renders a Lynx feature, call `ExpoLynx.prewarmRuntime()` after the
app is interactive so the first mount does not pay engine startup on the user's
critical path. See [First-render performance](/managed-delivery/performance/).
