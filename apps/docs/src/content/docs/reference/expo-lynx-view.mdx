---
title: ExpoLynxView
description: React component and module API for rendering a Lynx bundle inside an Expo host.
---

`ExpoLynxView` renders a compiled Lynx page as a native view. The default module
export exposes delivery and runtime helpers. The component and `checkForUpdate`
work the same on iOS and Android; `prewarmRuntime` is iOS-only and a no-op on
Android (see below). The web entry throws for native sources.

## `<ExpoLynxView>`

```tsx
import { ExpoLynxView } from 'expo-lynx-view';

<ExpoLynxView source={{ kind: 'managed', feature: 'delivery' }} style={{ flex: 1 }} />
```

The component extends `ViewProps` (except `children`). Layout is driven by the
parent — give it a real size, usually `flex: 1`.

### `source`

Exactly one of `source` or the deprecated `url` prop must be set.

| `source`                                 | Meaning                                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| `{ kind: 'managed', feature }`           | Verified local cache when present, otherwise the embedded baseline; checks the Worker after first render. See [lifecycle](/managed-delivery/lifecycle/). |
| `{ kind: 'embedded', feature }`          | Always the embedded baseline for that feature. No remote check.                          |
| `{ kind: 'development', url }`           | Loads directly from a dev-server URL. Debug builds only.                                 |

`feature` is typed as `LynxFeatureName`. After the first `expo prebuild`, the
config plugin narrows it to the union of configured feature IDs.

:::caution[`url` prop]

The bare `url` string prop is deprecated and accepted only by Debug iOS builds.
Use `source={{ kind: 'development', url }}` instead.

:::

### Props

| Prop          | Type                        | Notes                                                            |
| ------------- | --------------------------- | --------------------------------------------------------------- |
| `source`      | `LynxSource`                | Declarative source (above).                                     |
| `initialData` | `Record<string, unknown>`   | Serialized once and exposed to the page through `useInitData()`. Changing it after mount does not reload. |
| `style`       | `ViewProps['style']`        | Standard RN style. The view has no intrinsic size.              |
| `onLoadStart` | `(e) => void`               | Immediately before Lynx starts loading the selected bundle.     |
| `onLoad`      | `(e) => void`               | After Lynx finishes the first-screen layout.                    |
| `onError`     | `(e) => void`               | Delivery, verification, resource, or Lynx render failure.       |
| `onUpdate`    | `(e) => void`               | Managed-delivery check / stage / verified force-reload.         |

### Events

All handlers receive a `NativeSyntheticEvent`; read `event.nativeEvent`.

**`onLoadStart` / `onLoad`** — `LynxLoadEventPayload`

```ts
{
  url: string;
  feature: string;
  version: string;
  source: 'embedded' | 'cache' | 'development';
  durationMs: number; // load-start to first screen
}
```

**`onError`** — `LynxErrorEventPayload`

```ts
{
  url: string;
  feature: string;
  stage:
    | 'manifest' | 'signature' | 'compatibility' | 'download'
    | 'checksum' | 'resource' | 'archive' | 'lynx';
  code: string;
  message: string;
  version?: string;
  source?: 'embedded' | 'cache' | 'development';
  durationMs?: number;
}
```

A managed source keeps the last good render on screen when a background update
fails; `onError` still fires so the host can log it.

**`onUpdate`** — `LynxUpdateEventPayload`. Privacy-safe: no URLs, headers, paths,
or bundle contents.

```ts
{
  feature: string;
  phase:
    | 'checking' | 'disabled' | 'no-update' | 'downloaded'
    | 'staged' | 'reloading' | 'reloaded' | 'error';
  releaseId?: string;
  version?: string;
  revision?: number;
  code?: string;
  message?: string;
  durationMs?: number;
}
```

### Ref

```tsx
const ref = useRef<ExpoLynxViewRef>(null);
// ...
await ref.current?.reload();
```

`reload()` re-runs source selection and reloads the current bundle.

## `ExpoLynx` module

```ts
import ExpoLynx from 'expo-lynx-view';
```

### `checkForUpdate(options)`

```ts
ExpoLynx.checkForUpdate({ feature: 'delivery' }): Promise<LynxBundleUpdateResult>
```

Forces a managed-delivery check for one feature outside the automatic
post-render check. Resolves with `status: 'disabled' | 'no-update' | 'pending' |
'reloaded'` and, when a release is involved, `revision`, `releaseId`, and
`version`.

### `prewarmRuntime()`

```ts
ExpoLynx.prewarmRuntime(): Promise<void>
```

Builds the background JS runtime (engine + `lynx_core.js`) before the first
`ExpoLynxView` mount, so the mount attaches to a live runtime instead of paying
that cost while the user waits. Runs off the main thread; a second call while
one is already building is a no-op; on web it resolves silently.

Call it once the app is interactive, and ideally when the user is heading
toward the Lynx screen. See [Performance](/managed-delivery/performance/).

:::caution[iOS only]
On Android `prewarmRuntime()` resolves immediately and does nothing — the
native module does not implement it, so Android still pays engine
initialization at the first `ExpoLynxView` mount. The call is safe to make
unconditionally; it is a no-op there by design. A native Android warm-up is
tracked as separate performance work (see `docs/android-parity.md`).
:::

## Platform differences (iOS vs Android)

Managed delivery, the component, events, and `checkForUpdate` behave the same
on both platforms. The differences below are deliberate — mostly places where
the Lynx Android SDK has no equivalent of an iOS capability.

| Area | Difference | Why |
| --- | --- | --- |
| `prewarmRuntime()` | No-op on Android (resolves, does nothing). | A background Lynx runtime/shell is coupled to Android's threading model; deferred to separate performance work. |
| `<image>` (Lynx built-in element) | **iOS only.** On Android use `<x-lynx-fast-image>`. | No `ILynxImageService` is registered — Lynx's default (Fresco) conflicts with host dependencies. A per-view Glide-backed `LynxImageFetcher` is the planned path. |
| First-screen metrics (`first_screen_ms`) | On Android this equals `load_finished_ms`. | The Lynx Android SDK has no separate first-screen callback; iOS has `lynxViewDidFirstScreen`. Do not compare the two platforms' first-screen numbers directly. |
| Render-error `code` | Android emits `code: "ERR_LYNX_RENDER"` with the SDK's numeric code in `nativeCode`; iOS still emits the numeric code as `code`. | iOS-side alignment is tracked against the F-series. Switch on `code`; treat `nativeCode` as diagnostic only. |
| Prop-update batching | Android has no `OnViewDidUpdateProps`; `scheduleLoad`'s `post {}` coalescing achieves the same "apply the final prop set once" behavior. | Implementation detail — no observable difference. |

Everything else — `manifest` / `resource` / delivery error `stage` and `code`
values, `onUpdate` phases and their order, path containment for
bundle-relative resources — matches iOS.
